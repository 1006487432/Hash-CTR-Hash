# Hash-CTR-Hash

面向宽块加密算法研究的 Python 项目，聚焦 `HCH`、`HCTR1`、`HCTR2`、`XCBv1`、`XCBv2`、`XCB*` 等 Hash-CTR-Hash 类结构的实现、验证、对比与可视化展示。

这个仓库不只是“把算法代码写出来”，而是把一个研究型项目常见的三件事放在了一起：

1. 算法实现：把论文或标准中的结构落成可运行代码。
2. 实验验证：提供正确性、性能、统计安全性三类测试入口，并支持分类独立执行。
3. 汇报展示：通过原生 GUI 将结果组织成适合演示和横向比较的报告。

如果你需要准备组会、中期答辩、项目汇报，这个 README 的目标就是帮你从“会运行”提升到“能完整讲清楚项目”。

## 1. 项目要解决什么问题

传统分组密码工作模式通常一次只处理一个固定块长的数据块，例如 AES/SM4 的分组长度都是 128 bit。  
但在磁盘加密、数据库页加密、大块记录保护、可调加密等场景中，我们希望：

- 把一整段消息作为一个整体来加密，而不是简单逐块独立处理。
- 密文长度与明文长度保持一致。
- 在引入 tweak / associated data 后，同一消息在不同上下文下得到不同密文。
- 对消息任意位置的改动都能扩散到整段密文，而不是只局部影响。

这类需求通常会引向 `wide-block encryption` 或 `tweakable wide-block encryption`。  
Hash-CTR-Hash 结构正是这类设计中的经典思路之一：通过“哈希混合 + 计数器流 + 再哈希混合”的框架，把底层块密码扩展到对任意长度消息的整体加密。

本项目的核心价值，在于把多个典型方案放到统一框架下实现和比较，从而回答下面这些研究问题：

- 不同 Hash-CTR-Hash 家族方案在代码层面长什么样？
- 它们的输入接口、密钥结构、tweak/AD 处理方式有何不同？
- 在统一测试条件下，它们的正确性、速度和统计扩散表现如何？
- 哪些方案已有公开攻击研究，哪些更适合作为“安全设计”对照？

## 2. 这个项目的定位

这是一个**研究与教学导向**的项目，而不是生产环境密码库。

更准确地说，它适合以下用途：

- 课程设计、科研训练或组会汇报中的算法实现展示
- 宽块加密/可调加密方向的入门学习
- 论文复现前的代码框架准备
- 不同算法的统一接口测试与横向比较
- 为后续攻击复现、性能实验、GUI 演示打底

不建议把本仓库直接视为生产级密码组件，原因包括：

- 当前安全性测试仍以统计测试和研究提示为主
- 尚未集成正式的攻击复现实验
- 也没有做严格的工程级审计、恒定时间分析和生产部署封装

## 4. 先理解一个总图：项目如何分层

```text
用户/演示者
    ↓
GUI 页面（单算法测试 / 交叉对比测试）
    ↓
testing 层（正确性 / 性能 / 安全性测试编排）
    ↓
registry 层（统一算法注册表）
    ↓
algorithms 层（HCH / HCTR / XCB 各算法实现）
    ↓
common 层（AES/SM4、GF(2^128)、CTR、字节工具）
```

这套分层意味着：

- 算法实现和展示界面是解耦的
- 新增算法时，优先改算法层和注册表
- 新增测试时，优先改 testing 层
- GUI 只是“消费报告”，不直接写密码逻辑

这种结构对于课程汇报非常友好，因为它体现了清晰的软件工程思路，而不是把所有东西堆在一起。

### 5.1 `docs/`

这里保存的是理论背景材料，包含算法论文、标准文本和攻击研究。  
从文件名就能看出仓库已经在有意识地区分：

- 标准/方案文档
- 攻击研究文档
- 代码实现参考资料

这说明项目不是“闭门写代码”，而是以文献驱动的方式推进，非常适合答辩时说明研究依据。

### 5.2 `src/wideblock/common/`

这是底层公共组件，负责所有算法都会重复用到的基础能力：

- `aes.py`：AES 单块加解密
- `sm4.py`：SM4 单块加解密
- `gf128.py`：`GF(2^128)` 上的乘法，用于哈希混合
- `ctr.py`：CTR 风格的伪随机流生成
- `bytes.py`：补齐、分块、异或、长度编码等工具
- `types.py`：测试向量的数据结构

可以把这一层理解成“密码学积木箱”。

### 5.3 `src/wideblock/algorithms/`

这是项目最核心的一层，每个子目录对应一个算法家族：

- `hch/`
- `hctr1/`
- `hctr2/`
- `xcbv1/`
- `xcbv2/`
- `xcbstar/`

每个算法模块都对外暴露统一风格的接口：

```python
encrypt(key: bytes, plaintext: bytes, tweak_or_ad: bytes) -> bytes
decrypt(key: bytes, ciphertext: bytes, tweak_or_ad: bytes) -> bytes
```

统一接口的好处是：

- 测试层可以直接批量调用不同算法
- GUI 不需要关心每个算法内部细节
- 新算法容易接到既有框架中

### 5.4 `src/wideblock/registry.py`

这里是总注册表，用一个字典把“算法名”映射到“加密函数/解密函数”。

它的作用类似插件中心：

- `list_algorithms()`：返回可用算法列表
- `get_algorithm(name)`：返回指定算法的 `encrypt/decrypt`

所以整个项目实际上是“注册表驱动”的，而不是 GUI 直接 import 某个算法。

### 5.5 `src/wideblock/testing/`

这一层非常关键，因为它把“实验”做成了统一对象模型。

- `models.py`：定义 `TestResult`、`AlgorithmReport`、`ComparisonReport` 等报告结构
- `registry.py`：组织正确性、性能、安全性三类测试，并提供分类/流式执行入口
- `security.py`：实现随机性测试与雪崩效应测试
- `analysis.py`：实现内存占用与密钥扩展复杂度分析

你可以把这一层理解为“评测中台”。

### 5.6 `src/wideblock/gui/`

这是答辩展示最友好的部分，使用 `PySide6` 做了一个原生桌面 GUI。

核心页面有两个：

- `algorithm_page.py`：单算法测试结果页
- `comparison_page.py`：多算法横向对比页

GUI 的意义不是“炫技”，而是把研究项目中原本零散的终端输出，整理成：

- 概览指标
- 分类结果卡片
- 安全性图表
- 横向对比表格

这会大幅提升汇报时的表达效果。

## 6. 各算法家族在项目中的实现关系

如果你答辩时只讲文件名，老师会觉得项目碎；如果你能讲出“这些算法彼此是什么关系”，效果会好很多。

### 6.1 HCH

`HCH` 是典型的 Hash-Counter-Hash 结构：

- 前后两侧是哈希混合
- 中间是 CTR 风格处理
- 支持固定 16 字节 tweak

在本项目中：

- `hch_aes_*` 支持 AES，密钥长度可为 16/24/32 字节
- `hch_sm4_*` 支持 SM4，密钥长度固定 16 字节

代码特征：

- 使用 `GF(2^128)` 乘法完成哈希链
- 消息长度不少于 16 字节
- 对单块和多块情况分别处理

### 6.2 HCTR1

`HCTR1` 也是 Hash-CTR-Hash 类宽块结构，但实现风格更紧凑：

- 使用 32 字节密钥，并拆成 `K1 || K2`
- 其中一部分用于数据块加密，另一部分用于哈希
- tweak 固定为 16 字节

在本项目中：

- `hctr1_aes_*`
- `hctr1_sm4_*`

代码特征：

- 第一块与尾部数据通过哈希耦合
- 中间尾部通过 CTR 风格流变换
- 适合展示“哈希负责整体绑定，CTR 负责可变长处理”的思路

### 6.3 HCTR2

`HCTR2` 是该项目中最适合拿来讲“标准化与现代性”的一个算法，因为：

- 它有较明确的公开测试向量
- 项目中专门提供了向量加载器
- 实现中出现了 `POLYVAL`、`XCTR` 等比较现代的组件

代码特征：

- 采用 AES 单块操作
- 使用 `POLYVAL` 风格哈希
- 支持变长 tweak
- 要求消息长度至少为 16 字节
- AES 密钥支持 16/24/32 字节

项目中的 `tests/algorithms/test_hctr2.py` 直接读取测试向量验证加解密正确性，这一点非常适合在汇报中强调，因为它说明项目不仅有“自测”，还有“对照公开向量的标准校验”。

### 6.4 XCBv1、XCB*、XCBv2

这三个算法可以作为一个系列来讲：

- `XCBv1`：较早版本
- `XCB*`：在结构上做了改进
- `XCBv2`：进一步调整后的版本

它们共同体现的思想是：

- 把消息分成“一个 16 字节主块 + 其余数据”
- 利用哈希函数把主块、剩余块和 associated data 绑定起来
- 用 CTR 处理长尾部分
- 用额外块变换完成整体置换

在项目中：

- `xcbv1` / `xcbv1_sm4`
- `xcbstar` / `xcbstar_sm4`
- `xcbv2` / `xcbv2_sm4`

需要注意的实现差异：

- `xcbv1` 与 `xcbstar` 的 AES/SM4 接口都要求 16 字节密钥
- `xcbv2` 的 AES 版本支持 16 或 32 字节密钥，SM4 版本固定 16 字节
- `xcbv1` / `xcbstar` / `xcbv2` 都把第三个参数视作 `associated_data`
- `HCH` / `HCTR1` 更偏向固定长度 `tweak`

### 6.5 如何在答辩中概括这些算法

你可以用一句话把整个项目概括为：

> 本项目围绕宽块加密中的 Hash-CTR-Hash 思想，实现了 HCH、HCTR 和 XCB 系列多种代表性方案，并在统一接口下完成正确性、性能与统计安全性的实验框架搭建。

这句话既说明了研究对象，也说明了工程成果。

## 7. 项目采用了怎样的统一接口

项目中所有算法都被统一抽象成：

- 输入：`key`、`plaintext/ciphertext`、`tweak 或 associated_data`
- 输出：同长度的 `ciphertext/plaintext`

统一接口背后有两个很重要的设计点：

### 7.1 统一了调度方式

测试层不需要关心这是 HCH 还是 XCB，只需要：

1. 从注册表取出算法
2. 调用 `encrypt`
3. 调用 `decrypt`
4. 检查往返恢复是否成立

### 7.2 保留了算法差异

虽然外部接口统一，但内部约束没有被抹平，例如：

- HCH/HCTR1 需要固定 16 字节 tweak
- XCB 家族接受 associated data
- 各算法对密钥长度要求不同
- 所有已实现宽块算法都要求消息长度至少为 16 字节

这体现了一个好的实验平台应该做到的事：**接口统一，但不篡改算法本身的语义。**

## 8. 测试体系是怎么设计的

这是本项目最值得讲的软件工程亮点之一。

### 8.1 正确性测试

入口在 `src/wideblock/testing/registry.py` 中的 `run_correctness_suite()`。

它会：

- 为每个算法生成确定性的伪随机样本
- 构造不同长度的明文
- 调用加密与解密
- 检查是否能准确恢复原文

默认关注的消息长度包括：

- 16 字节
- 31 字节
- 128 字节

也就是说，它兼顾了：

- 刚好一块
- 非整块长度
- 较长消息

这是为了覆盖宽块算法最常见的边界情况。

### 8.2 性能测试

入口在 `run_performance_suite()`。

它会对多个消息规模进行重复测量，统计：

- 平均加密耗时
- 平均解密耗时
- 加密/解密吞吐量
- 周期/字节（cpb）
- 峰值内存占用
- 密钥扩展复杂度分析
- 测试轮数

当前选取的规模有：

- 16 字节
- 256 字节
- 4096 字节

这三档分别对应：

- 小消息延迟
- 中等消息处理
- 较长消息吞吐

其中 `cpb`（Cycles per Byte）用于衡量“每个字节平均消耗多少 CPU 时钟周期”，相比直接比较 MB/s，它更适合做不同主频机器之间的横向比较。当前实现会优先读取 `psutil` 提供的 CPU 频率信息，若运行环境无法提供频率，则该指标会自动标记为不可用，而不会中断整套性能测试。

### 8.3 安全性测试

入口在 `src/wideblock/testing/security.py`。

当前实现的是两类**统计型补充测试**：

- 密文随机性测试
- 雪崩效应测试

这两类测试的定位一定要讲清楚：

- 它们可以作为实现质量和扩散效果的辅助观察
- 但不能替代密码学安全证明
- 更不能替代针对具体结构的区分攻击或恢复攻击复现

也就是说，这里的“安全性测试”更准确地说是“统计安全表现测试”。

### 8.4 研究提示机制

项目中对 `xcb` 家族额外加入了安全提示：

- 若算法名以 `xcb` 开头，测试报告会加入 `WARNING`
- 用于提醒这类算法已有公开研究，不应仅凭统计测试就判断安全

这一点很适合在答辩时体现你的严谨性：  
**项目没有把“随机性看起来不错”误写成“算法就是安全的”。**

## 9. GUI 的意义是什么

这个项目的 GUI 不是可有可无的壳，而是研究展示层的一部分。

### 9.1 单算法页

单算法页面会展示：

- 算法名称
- 总通过项数、失败项数、总耗时
- 正确性 / 性能 / 安全性三个独立标签页
- 每类测试单独运行按钮与进度提示
- 性能图表：时延曲线、吞吐量曲线、周期/字节曲线、峰值内存曲线、密钥扩展复杂度卡片
- 安全性图表：随机性比例条、字节频率分布图、卡方历史曲线、雪崩翻转分布图

它适合在组会中回答“某个算法具体表现如何”。

### 9.2 交叉对比页

交叉对比页会展示：

- 独立的“性能交叉对比”和“安全性交叉对比”页面
- 性能横向图表：加密/解密时延、吞吐量、周期/字节、峰值内存、密钥扩展复杂度
- 安全性横向图表：随机性比例、卡方值、卡方历史趋势、雪崩效应
- 逐步更新的进度提示与对比结果表

它适合在答辩中回答“为什么要做成平台，而不只是实现一个算法”。

### 9.3 GUI 的方法论价值

GUI 的真正意义是把研究流程标准化：

- 算法实现标准化
- 报告结构标准化
- 对比方式标准化
- 演示方式标准化

因此，GUI 不是附属品，而是“研究工具产品化”的体现。

## 10. 如何运行项目

### 10.1 安装依赖

```bash
pip install -r requirements.txt
```

依赖包括：

- `PySide6`：GUI
- `pycryptodome`：密码学底层实现
- `cryptography`：部分密码学支持
- `numpy`、`scipy`：统计随机性测试与数值计算
- `psutil`：读取 CPU 频率，用于估算周期/字节（cpb）
- `pypdf`、`PyMuPDF`：文档相关处理

### 10.2 启动 GUI

```bash
python run_gui.py
```

启动后可以：

- 单独运行某个算法的正确性、性能或安全性测试
- 选择多个算法做性能交叉对比或安全性交叉对比
- 在测试进行中查看进度条和局部结果更新

### 10.3 运行脚本测试

可直接执行：

```bash
python tests\algorithms\test_hch.py
python tests\algorithms\test_hctr1.py
python tests\algorithms\test_hctr2.py
python tests\algorithms\test_xcbv1.py
python tests\algorithms\test_xcbv2.py
python tests\algorithms\test_xcbstar.py
python tests\test_registry.py
```

其中：

- `test_hctr2.py`：基于向量验证，更像“标准对照测试”
- 其他部分算法测试：更偏向 round-trip 验证
- `test_registry.py`：检查统一注册机制是否正常

## 13. 组会/中期答辩可以怎么讲

如果你需要 3 到 5 分钟快速讲清楚项目，可以按这个逻辑：

### 13.1 背景

- 宽块加密适用于需要整体保护一段数据的场景
- Hash-CTR-Hash 是构造可调宽块加密的重要设计思路
- HCH、HCTR、XCB 系列是该方向的代表性方案

### 13.2 本项目做了什么

- 实现了多个代表性宽块算法
- 为它们设计了统一调用接口
- 搭建了正确性、性能、统计安全性测试框架，并支持分类独立运行
- 进一步做了 GUI，用于单算法展示和多算法对比

### 13.3 技术路线

- 底层基于 AES/SM4、GF 运算、CTR 组件
- 中层实现各算法结构
- 上层通过注册表统一调度
- testing 层输出结构化报告
- GUI 消费报告并可视化展示

### 13.4 当前成果

- 已完成 11 个算法入口接入
- 已有脚本测试与 GUI 实验平台
- HCTR2 已接入公开向量校验
- XCB 家族已加入公开研究风险提示
- 性能页已支持时延、吞吐量、周期/字节、内存占用和密钥扩展复杂度展示

### 13.5 后续工作

- 增加更多论文向量和标准向量
- 接入攻击复现实验
- 扩展更完整的性能基准
- 强化安全性分析与实验覆盖

## 14. 这份项目最值得强调的创新点或亮点

如果老师问“你的工作量和价值体现在哪里”，建议重点强调这四点：

1. 不是只实现单一算法，而是统一实现了多个宽块方案，并做了家族化比较。
2. 不只是写密码代码，还搭建了测试与展示平台，形成完整研究链条。
3. 对正确性、性能、统计安全性做了统一建模，便于扩展与复用。
4. 对已有公开攻击研究保持谨慎态度，没有把统计测试误当安全证明。

## 15. 当前局限与后续扩展方向

当前局限：

- 安全测试仍以统计观察为主
- 尚未系统集成论文攻击复现
- 一些算法主要做 round-trip 验证，缺少更多外部标准向量
- 性能测试仍是基础 benchmark 版本，尚未纳入 CPU 绑定、核隔离等更严格控制变量

建议优先扩展的位置：

- `src/wideblock/testing/security.py`

- `src/wideblock/gui/pages/algorithm_page.py`
- `src/wideblock/gui/pages/comparison_page.py`

未来可以继续接入：

- 论文中的区分攻击/恢复攻击复现
- 更多边界条件测试
- 随机测试规模扩大
- 覆盖率统计
- 自动导出实验报告
- 更多算法家族
